# Grid-import warnings: default-off integration and measurement verification

Status 2026-11-03: scheduled adapter, shared outbox, cached status and verified-setup-only bot settings implemented with synthetic tests; **no deployed grid alert or production grid polling yet**. Existing battery notifications are unchanged. The owner's latest priority is warning about grid purchases, especially alongside a current EV charging report, while permitting ordinary household battery discharge at night.

## Independent rules

- Grid import is a distinct measured source, not a battery-discharge/SOC inference. A grid warning must work day and night independently of the daytime battery window and should not depend on an EV report being present.
- Preserve the owner's existing 3 kW / 15-minute daytime battery rule. Nighttime household battery use is expected; no generic nighttime discharge alarm or EV-causation claim is introduced.
- EV charging evidence remains manually confirmed/directly measured/unknown. A warning may say the owner reported charging, but cannot attribute aggregate grid import to the EV. A charging report does not grant an overnight exception.
- A household reserve/low-SOC warning is a separate future rule; the 13% grid-fallback setting is not verified import and is not an automatically chosen reserve target. Baseline household use, morning target and warning margin remain missing.

## Pure implementation

src/grid-import.ts is now imported by the default-off Worker adapter (the earlier foundation excluded it). decodeGridReading requires an explicit supported point, direction and confirmed independent reference; it checks unique dataList selection, exact W unit, finite number or strict decimal-string value, valid seconds-based device collection time and exact freshness. Export becomes zero import only under the confirmed direction. Missing/null/wrong unit/duplicate/stale/future/unverified samples are unavailable and never borrow battery units or station time.

advanceGridImport takes an explicitly selected threshold/re-arm/duration, bounded source identity and source readings. Distinct fresh samples spanning elapsed duration are required. Duplicates/out-of-order samples cannot advance; dips, unavailable data, excessive gaps and stale/future values cannot establish sustained import. Strict hysteresis rearms only below the re-arm value. Candidate creation latches the episode; the original candidate expires after ten minutes. Policy/source changes restart confirmation, corrupt companion metadata fails with fixed diagnostics, rollback preserves the clock high-water mark and metadata stays bounded. There is no timezone/EV dependency and no IO, mutation of inputs or growing history.

## Scheduled integration and safety gates

`gridImport` is omitted by default; canonical `{enabled:false}` is also accepted. Enablement requires the eight required fields for the supported point/sign, positive threshold/re-arm, whole 1–120 minute duration, `referenceConfirmed:true` and `allHoursConfirmed:true`; optional boolean `recovery` defaults off. The verified device identifier lives only in the owner's `GRID_DEVICE_SN` secret. It is not a public config or CI-snapshot field. A private SHA-256 source digest covers region/station/device/point/sign/verification version; source or policy changes restart grid confirmation without changing battery latches.

An eligible successful station request is followed by one selected-device `/device/latest` batch on the same Deye client/token. Exact matching device, point, W unit and device collection time are required. Optional grid failure has its own bounded 5/10/20/40/60-minute cooldown and cannot increment station failures or suppress valid battery alerts. Global provider cooldown makes no device call and suppresses grid delivery without a current source observation. Missing, stale or invalid samples do not become zero import. Corrupt optional metadata is retained with fixed diagnostics while only grid pending events are removed; a rollback preserves its clock high-water mark even across policy changes.

The grid event shares the existing **two total slots, two send attempts per invocation and two monitor checkpoints**. Grid has priority over battery, health and recap. Admission evicts recap first, then settles/abandons health, then discharge before full if necessary. Battery admission cannot create a third slot. Original ten-minute candidate expiry and three delivery attempts are preserved; a retry beyond expiry is abandoned. Before sending, source/policy/current freshness, measured import and original expiry are checked again. A dip cancels stale advice; a latched episode does not generate repeated reminders. KV remains eventually consistent: API acceptance is neither exactly-once delivery nor owner receipt.

Grid warnings are all-hours and do not inherit the four-category quiet-hours consent (full/discharge/health/recap). Explicit separate grid all-hours consent is required. They show measured kW/time, cloud-delay wording, and manually reported/unknown EV status without claiming EV causation or granting overnight permission. No weather lookup is triggered by a grid event.

## Telegram grid menu and recovery notice (2026-11-03)

The owner requested all three follow-ups: a grid settings menu, optional recovery notice and a separate house-battery reserve warning. `/settings` now offers **Grid alert settings** for an already verified enabled grid source; `/grid` opens it directly. Choose a kW preset (0.3/0.5/1/2/3, above the configured re-arm), a duration (5/10/15/30/60 minutes) or recovery on/off. Selection only previews; Confirm saves and Cancel preserves settings. Custom commands remain available, including `/grid_recovery on|off`. The menu cannot choose a sensor, verify a mapping or enable an off/unverified source.

Callbacks retain their original 30-minute expiry and hash of current station/grid policy/private source context. The hash is a change guard, not authorization/proof of issuance. Owner/chat/header/replay/rate/day checks run before actions; each tap uses the existing one bot write, optional acknowledgement and one reply, with no monitor write or provider request. No pending-menu state/key is added. Payloads fit Telegram's 64-byte limit. Source/policy edits invalidate the menu. Existing battery menus/commands remain independent.

`gridImport.recovery:true` is explicitly opt-in, omitted/false by default. The monitor records one bounded recovery episode only **after Telegram accepts a grid warning**; that is not proof of owner receipt. Recovery requires two distinct fresh readings below the owner's grid re-arm value spanning at least five minutes. Missing, stale, out-of-order data and gaps cannot become zero or establish recovery. A small positive import is labelled **“Grid import back below your re-arm level”**, with measured kW/time, rather than claiming grid use stopped or the EV stopped. Turning recovery off removes its metadata/pending notice on the next running tick. Enabling it does not reconstruct a prior warning history.

A recovery candidate has the original ten-minute expiry and three-attempt cap; it cannot add another queue slot/checkpoint or renew itself after expiry/eviction. Current source/policy/freshness and below-re-arm condition are rechecked before send. Priority is now **grid warning > reserve warning > battery full > battery discharge > grid recovery > health > recap**, within two slots/two send attempts/two monitor checkpoints. An evicted episode is consumed rather than generating a catch-up flood. Grid recovery and explicitly consented all-hours reserve notices are outside the existing four quiet categories.

No provider call, KV read/key/write slot or growing history is added by these follow-ups. The seven-Deye-attempt/ten-external-attempt maximum and calculated 864/912-write and 960-read scenarios retain their prior assumptions; typical cooldown writes/bounded validation/hash CPU can increase.
