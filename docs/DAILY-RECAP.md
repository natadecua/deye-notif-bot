# Optional daily cached recap: design gate

Status **2026-10-27: pure preparation and shared rendering implemented; delivery remains proposed, unavailable and undeployed**. The isolated `src/daily-recap.ts` helper is not imported by the Worker and adds no accepted deployment config/state field. Existing `/status brief` now uses `src/snapshot.ts`, an owner-requested cached view with no scheduled dispatch. This document specifies a future opt-in reminder of that view. It is not a daily energy report: no sample history, daily totals, savings, charging prediction or household reserve calculation exists.

The owner has chosen Asia/Manila for daytime alerts, but has **not chosen a recap time or enabled a recap**. Do not infer consent from that timezone, commands, weather, health notices or an active charging report. Nighttime battery use remains for the house; consenting to an informational message never grants an overnight EV exception. Reserve/urgent-night planning still needs the inputs in [RESERVE-ALERTS.md](RESERVE-ALERTS.md), and optional measured fields retain their [evidence gate](MEASURED-CONTEXT.md).

## Owner journey and configuration contract

A future offline setup flow must explain the cached-only content, the possibility of stale/missing data, missed deliveries and the absence of history. It must ask separately whether to enable a recap, confirm an IANA installation timezone, choose an hour/minute and confirm saving. There is no preselected hour, timezone inferred from location, automatic opt-in, new secret or deployment. Cancellation retains the previous settings. Saving local settings requires a separate manual release or private CI snapshot update.

The proposed optional configuration block is `dailyRecap`; **it is not currently supported deployment configuration**. The standalone `validateDailyRecap` helper accepts a policy argument only: omission/canonical `{ "enabled": false }` return off; on requires `enabled: true`, a bounded valid `timeZone` (at most 64 characters), integer `hour` (0–23), integer `minute` (0–55 in five-minute steps), and `scheduleConfirmed: true`. It rejects other fields, partial consent, invalid zones and coercions. Setup, runtime config validation and the private CI allowlist do not call it yet; they must share validation before any enablement release. Keep the public template off by omission.

When daytime discharge already has a timezone, require the recap zone to match and ask the owner to confirm it explicitly. Without a daytime policy, require an explicitly selected recap zone; this must not change battery-alert display/window settings. Explain that the selected local time can be at night and that daylight-saving transitions can skip or repeat clock times. Confirmation permits only the informational message at that schedule. General quiet hours remain unimplemented; future quiet hours must suppress/expire recaps without an emergency bypass or morning replay.

Commands are optional: with commands disabled, a recap can show battery data and unknown EV status, but must omit unusable command links. With commands enabled, reuse the monitor's existing bot snapshot and effective preferences. Do not add a bot read just for manual EV evidence, mutate its session, spend/reset the webhook command allowance, add buttons or register a command. Before enabling delivery, authorized settings/status and offline summaries must separately label recap configured off/on/paused and its chosen zone/time. Configuration is not proof of operation or receipt.

## Cached content and evidence

The pure bounded `renderBriefSnapshot` is now extracted from existing brief status; do not call the webhook handler or copy its authorization/IO into Cron. Compatibility tests preserve existing command output and IO. The helper's explicit recap presentation has the fixed title “Battery snapshot · daily recap”, followed by:

- Cached charge and battery discharge, the original source timestamp with timezone/offset, exact-age freshness label and the cloud-delay note. Missing data stays missing; future-dated data is explicitly not current. Do not replace source time with send/poll time or count a duplicate as a new observation.
- Unknown load breakdown, plus existing cached retry/cooldown context with cause unknown. Stale values may be displayed only as old cached measurements, never current headroom or charging advice. The recap does not diagnose an outage or emit/acknowledge a health episode.
- Separate expiring **user-reported** charging/not-charging evidence only from the already available snapshot, revalidated at send time. Expired/future reports mean unknown. A configured profile is nominal reference data, not measured EV current or power. Directly measured EV status remains unavailable until a supported source is validated.

Keep the entire reply within a tested 1,000 UTF-16 code units, including essential freshness/evidence text and maximum valid labels/timestamps. Do not truncate away that context. Omit profile lists, weather values and health lifecycle metadata; an enabled-command installation may link to `/status` for existing cached detail. No weather refresh, extra Deye request, forecast-based recommendation, reserve claim, new measurement field, equipment control or EV-causation claim is permitted. Use fixed safe fallback text rather than identifiers, upstream bodies, exception text or secret-bearing URLs. Render again from the current invocation's validated cache at every attempt; do not persist a message body or old manual report in the outbox.

## Local slot, expiry and clock rules

Use the existing five-minute Cron; no second trigger, alarm or sleep-until-scheduled loop. The proposed opportunity is the chosen local minute through **less than 15 minutes afterwards**, truncated at local midnight. A delayed invocation is eligible only while inside that opportunity; this is not an exact-time or receipt guarantee. This 15-minute delivery opportunity is independent of the owner's 15-minute sampled-discharge tolerance and health warning duration.

1. On first activation, legacy state, measurement-identity change or schedule-policy change, silently consume the current local date and cancel only recap candidates. The earliest new opportunity is a later local date. Enabling late today must not generate an immediate catch-up message. A recap-only policy change must preserve battery cycles, health episodes, retries and cached readings.
2. Track a monotonic resolved-local-date high-water mark and last observed absolute time. A date at or below the resolved mark cannot create a candidate. Before today's chosen minute, do not create one. At the first observation in its eligible interval, resolve/consume that date whether a slot can be admitted or must be skipped for capacity. After the interval, resolve it as missed. On a forward jump, consider only today's opportunity, never iterate through missing dates. Persist the resolution in the shared first checkpoint before any send.
3. Derive the candidate's original absolute due time by subtracting the local minute/second/millisecond difference from the current instant. Round-trip that instant through the chosen zone and require the same date and chosen hour/minute. A failed round-trip (including a skipped spring-forward time) consumes the date without sending. Do not search an unbounded calendar or allocate a per-zone formatter map.
4. Fix `expiresAt = originalDueAt + 15 minutes`; it never starts at admission, retry, restart or later availability. Send only while `now < expiresAt`, the local date still matches, and the local minute remains inside the original opportunity. Exactly at expiry or midnight, drop it. Recheck policy, clock, local date/window and expiry after all waits and immediately before sending.
5. In a repeated daylight-saving hour, the first **observed eligible occurrence** can resolve that date. If already resolved in the first occurrence or marked missed, the second cannot recreate it; if the date is still unresolved, the second can be the sole opportunity. Once a candidate exists, a fold does not renew its absolute expiry. A jump outside its local interval consumes/cancels it. Include offsets in displayed timestamps rather than implying the local clock is unique.
6. If the absolute clock moves backwards, suppress/cancel recap delivery and retain the date/time high-water marks until the clock catches up. Never decrease a resolved date or mint another candidate from the repeated interval. Invalid/unrenderable clocks suppress recap with fixed diagnostics. An ordinary process restart must retain the original slot, expiry, attempts and consumed date.

“Consumed” means no further recap candidate for that date under stable persisted state; it does not mean delivered. Opting off then on, or changing zone/time repeatedly, suppresses each new activation date instead of creating extra opportunities. A missing/reset record cannot prove prior sends; initialization still skips its current date. KV lag, overlapping invocations and crashes can duplicate or lose effects despite these sequential rules. Do not promise exactly-once, at-least-once, or one received message per day.

## Bounded state, priority and transport

Propose one optional, independently validated recap metadata block in `monitor:v1`: version/policy identity, resolved date and last observed absolute time. Keep it below 1 KiB serialized, including any fixed lifecycle flags. Retain no per-day map, sample series, report history, delivered-message IDs, raw payload or new KV key. The existing two-slot outbox may contain **at most one** validated recap event with fixed policy/date identity, original due/expiry timestamps, attempts and next-attempt time; it carries no fabricated `Reading`, manual session or rendered text. Field-level schemas and bounds require tests before implementation.

Admission and dispatch order is **battery events, then health, then recap**, preserving existing relative order/timing within each higher-priority class. Resolve recap only after battery/health transitions. If both slots are occupied, skip the recap for that date: no hidden waiting queue. Battery admission evicts recap before health; health admission may evict recap but never battery. Eviction consumes the recap date. It does not reset a battery latch, consume a health episode, postpone a higher-priority retry or generate a replacement recap later that day. Audit every kind-specific filter/expiry/send/decoder branch; a new event must not accidentally enter the battery-reading path or be treated as battery capacity.

Keep the existing **two total Telegram attempts per invocation** across all kinds, one attempt per event per tick. Use the existing bounded transient retry policy (at most three lifetime attempts, five/ten-minute delay with jitter and provider Retry-After). A recap may expire before those attempts fit. If the next attempt would meet/exceed its original deadline, abandon it immediately. Permanent errors, exhaustion, expiry, eviction and accepted sends remove it while retaining the consumed date; never remint it with a fresh deadline. API acceptance is not owner receipt.

All admission/consumption/attempt eligibility uses the same first monitor checkpoint; a failed checkpoint means no Telegram send. All delivery results share the existing single final checkpoint, spaced at least 1.1 seconds after the first write. No per-event write, lock key, third checkpoint or extra retry loop. A crash after Telegram acceptance but before results can duplicate; a failed checkpoint can lose progress. Preserve fixed sanitized failure codes.

Recap send eligibility is independent of a fresh Deye result: an explicitly labelled missing/stale snapshot can be delivered during provider failure/cooldown. It must never release stale battery advice, bypass the Deye cooldown or request auth/weather. The current early cooldown return must be revised only when recap work/cleanup exists; recap-off legacy paths retain their exact behavior. Enabled cooldown ticks may need one shared monitor write (two on delivery), even when health is off. Whole-monitor disabled mode retains its zero-KV/zero-provider/zero-send early return; it cannot observe changes while disabled.

## Resource and migration gates

The proposed budget reuses existing operations under the documented single-station, stable valid-KV, non-overlap assumptions:

| Resource | Required envelope before delivery is enabled |
| --- | --- |
| Schedule / reads | Same 288 scheduled ticks/day; no additional key/read. With optional existing commands, the documented combined read estimate remains 960/day. |
| Writes | At most two monitor checkpoints plus one token-cache write/tick: 864/day; plus 48 normal command writes = 912/day. Typical cooldown writes can increase. There is no additional write per recap event. |
| External attempts | At most six existing Deye attempts, two shared Telegram attempts and one existing discharge-only weather request = nine/tick. At most three Telegram attempts per resolved recap date, within its original opportunity; no provider refresh for recap. |
| State / CPU | Less than 1 KiB recap metadata, one recap inside two total events, bounded text, no history/dependency/unbounded timezone search. Added formatter/render/decoding and cold-bundle CPU must be measured on Free. |

The [official Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [KV limits](https://developers.cloudflare.com/kv/platform/limits/) were rechecked on 2026-10-27: Free Cron CPU is 10 ms, with 1,000 daily KV writes and one write/second/key. This document's arithmetic is a design budget, not measured viability or an account-wide quota guarantee. Other workloads, manual runs, KV lag, concurrent invocations and configuration churn retain the caveats in [CLOUDFLARE-LIMITS.md](CLOUDFLARE-LIMITS.md). No paid service/plan is assumed; reduce/defer delivery if measurements cannot fit.

Legacy records/configuration remain recap-off without a state rewrite merely to add absent metadata. Malformed optional metadata must suppress only recap with a fixed code and preserve battery/health state; malformed essential state or queue remains fail-closed. Policy changes and opt-out remove only recap records/events. Cleanup during Deye cooldown may share one checkpoint. Before manually rolling back to a binary that rejects recap event kinds, turn **recap only** off with monitoring enabled, allow a successful cleanup checkpoint and verify it privately. Do not reset the whole state or remove health/battery events. Whole-monitor pause/identity-reset limitations must be explained; no live rollback has been performed.

## Future acceptance matrix and staged implementation

The pure preparation slice has **24 synthetic cases** in `test/daily-recap.test.ts`: the initial scaffold produced 21 behavioral failures and two compatibility passes before implementation; a later malformed-identity rollback case also failed before its fix. All 24 now pass. The two originally passing off/monitor cases are compatibility evidence, not new TDD claims. Metadata stays below 1 KiB across 128 simulated dates; one long-gap case asserts at most three formatter calls. There is no calendar scan, IO, history or added runtime dependency. Helpers require an already validated base `Config` and return copied bounded metadata. `resetPending` signals activation/policy change or rollback; a future caller must cancel recap only, and persist date consumption before any send. Returned candidates are single preparation results, not a hidden queue; future outbox code must retain original expiry/attempts. This stage never writes a monitor field or sends a message.

The shared-view slice has **14 synthetic unit cases**, initially 12 behavioral failures and two compatibility passes, plus one synthetic workerd renderer-harness case observed failing before implementation. Existing authorized brief output/IO and detailed authorization remained compatible before and after extraction; existing rendering is not retroactively labelled test-first. Command-disabled rendering ignores supplied bot reports and omits dead links. An explicit display zone affects source/retry/report labels only, without changing configuration or source/session instants. The workerd harness renders with actual Workers Intl and no outbound request; it is not a production recap endpoint or scheduled-delivery test.
