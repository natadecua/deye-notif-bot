# Architecture and failure semantics

One owner's Cron invocation → Deye regional REST API → validated station reading → pure alert state machine → persistent KV outbox → Telegram. Configuration is a JSON Worker variable bundled by Wrangler. Credentials are Cloudflare Secrets. Optional owner-authorized Telegram updates use a dedicated secret-header webhook and a separate small KV record. There is no database of users, public polling endpoint or equipment-control endpoint.

## Interpretation and alert state

`monitor:v1` holds a versioned, small JSON object: last accepted timestamp, two armed flags, the high-discharge counter, API cooldown and up to two pending events. Invalid persisted state fails closed with `state_invalid`; it is not silently reset. A first deployment starts both flags armed. Changing the station, region, units, timestamp mode, thresholds or freshness limits intentionally starts new alert cycles and discards old pending events. Notification switches, EV hints/profiles and bot/chat changes preserve battery cycles. Initial state identities that appended the EV object are migrated by matching the ten measurement-interpretation fields; no latches, timestamps or confirmation counts are lost solely because hint settings changed.

It optionally also holds `latestReading`, updated only on accepted readings for cached `/status`. Legacy records without it remain valid. Webhook commands never write `monitor:v1`, poll Deye or alter battery latches. They write `telegram:v1`: a station-context identity, bounded UTC command counter, last update/time, optional validated preference overrides and one manual session with a six-hour expiry. With commands enabled, Cron reads that record once and applies preferences before existing transitions. Manual session fields do not enter the battery-state identity.

Authorized status also renders existing `apiRetryAt` as cached update context from that same read. Disabled monitoring takes precedence, then a future cooldown, an elapsed positive threshold, or no recorded delay/waiting for a reading. It deliberately does not derive a cause from `apiFailures`: invalid telemetry and provider failures share the cooldown mechanism and no cause is persisted. Fresh/stale reading labels, weather and manual EV evidence remain independent. It uses only fixed text plus an eligible formatted threshold; unrenderable retry dates get a fixed unavailable note, while essential state validation still fails closed. No raw metadata/error field is displayed. The helper cannot fetch, write/reset monitor state or create a health event; current retry/freshness/outbox rules remain unchanged. Retry eligibility is not a scheduled-time/recovery guarantee and KV remains eventually consistent.

Optional `/status brief` branches only after that same authorized monitor read and reuses the update-state renderer with a compact text mode. The fixed-shape brief measurement view skips weather decoding/profile-reference lists, retains source age/time and unknown load breakdown, and appends the existing manual-report summary without renewing it. Health flags are configuration only; optional lifecycle metadata is not inspected. The exact source-age comparison precedes display rounding in both views, fixing the detailed view's subsecond stale-boundary discrepancy. Default detailed layout/command handling and provider/KV budgets remain intact. Brief rendering adds no schema/state field, dependency, history or control. Tests cover the 1,000-unit reply bound and unchanged cache bytes; added rendering/bundle CPU remains unmeasured in production.

Help/start now offer three fixed read-only navigation buttons. A pure helper maps only whitelisted view names with canonical safe-integer timestamps less than 30 minutes old, after existing webhook authorization/replay/budget checks. Future/expired/malformed navigation gets fixed guidance without reflecting payloads. Valid navigation enters the existing status/settings handlers and bypasses charging/profile selection; old message text cannot select a mutation. Menu age is not proof of issuance or authorization. No nonce/history/hash/provider/KV key is added. Help keeps its one-read/write/reply path; taps reuse existing callback acknowledgement/reply caps and one replay write, with a monitor read only for status. Session/preferences/cache bytes are preserved, and callback acknowledgement failure never suppresses the reply. Old charging/profile callbacks retain their existing path. CPU and live rendering remain manual-release checks.

The [daily cached recap contract](DAILY-RECAP.md) now integrates pure preparation with scheduled monitoring, default off by omission. Shared runtime validation accepts canonical off or an explicitly consented local zone/hour/minute; when a daytime zone exists, it must match. Policy validation moved to a separate module to avoid a configuration/preparation import cycle, retaining the existing pure helper exports. Optional `dailyRecap` metadata shares `monitor:v1`; one strictly decoded `recap` event carries its original slot and no fabricated reading/body. Activation/policy changes skip the current local date, and missed/capacity-skipped/evicted/expired dates never remint a candidate under stable persisted state. Corrupt optional metadata suppresses recap with a fixed code while preserving battery/health; malformed queue records remain fail-closed.

Battery admission evicts recap before health; health may preempt recap. Admission/dispatch retains battery > health > recap order within two total events/Telegram attempts. Recap admission happens after battery/health transitions, and all resolution/results share the existing first/result checkpoints. Its independent send gate can show labelled stale/missing cache on provider failure/cooldown without enabling battery advice or calling Deye/auth/weather during cooldown. Source/manual freshness is reevaluated from current invocation snapshots at send time. Original expiry, local midnight, policy and rollback guards are rechecked after waits. Retries use existing delays/Retry-After/attempt caps; a next retry at or beyond the original recap deadline is abandoned. API acceptance/results failures retain the documented duplicate/lost-effect caveats.

Recap-only opt-out removes its metadata/events during cooldown in one checkpoint and preserves battery/health state. Omitted/off legacy records add no metadata, read, write or provider call; whole-monitor disabled mode remains zero IO. Enabled cooldown ticks can increase typical writes to one checkpoint, or two on delivery, without changing the calculated daily ceiling. Pre-integration binaries reject recap kinds: disable recap only with monitoring enabled and privately verify cleanup before manual rollback, without resetting battery state. Defaults/private settings stay off and production CPU/live release gates remain.

The shared `renderBriefSnapshot` now owns complete brief text, including the existing manual-report summary, while `cachedUpdateStatus` is reused by detailed status. The authorized brief path keeps its two reads/one replay write/one reply and valid reply text; detailed status retains its existing layout. Pure rendering accepts decoded records and a caller clock, never advances health/scheduling and does not inspect optional raw weather/health metadata. Command-disabled use omits dead links and treats EV evidence as unknown. A fixed recap title and explicit display-only zone prepare future reuse without creating a daytime policy. `displayTimeInZone` shares the existing bounded formatter; an optional expiry formatter reuses the manual evidence/expiry engine without renewal and supplies fixed safe time fallbacks. No endpoint, schedule, state/config field or provider/KV operation is added. Tests cover exact existing replies, freshness/expiry/timezones, a complete 1,000-unit bound and a synthetic workerd renderer harness with zero outbound IO. Extra bounded branches/bundle CPU remain unmeasured in production.

The offline `configureRecap` helper now validates before prompting and clones settings. Independent opt-in, explicit zone/hour/minute (no defaults), schedule consent and final-save consent prepare only a local change. Cancellation preserves previous settings; opting out removes only recap configuration. Shared strict validation gates prompt results, pure summaries and CI's five-field allowlist. Pure summaries extend preferences and existing status/settings with configuration off/on/paused, independent battery switches and unverified operation/receipt. Brief rendering retains the complete 1,000-unit bound and omits dead links when commands are off. No lifecycle read/advancement, cache write, new provider/KV operation, bot override or mutation command is added. Synthetic helpers never read owner files or deploy; the real CLI persists only after the helper returns successfully. Fixed recovery names only the local recap block. Added bounded validation/text/formatter work and bundle size require production CPU measurement.

The existing synthetic demonstration now reuses `configureRecap` for two illustrative explicitly entered schedules, separate schedule/save consent, both cancellation paths, invalid saved consent rejected before prompts and explicit opt-out. It verifies retained in-memory settings and finishes health/recap off, without extra transports, owner-file/environment access or snapshot output. The production Worker is unchanged by this rehearsal. Natural scheduling, receipt, production CPU/quota and manual release evidence remain installation gates; general quiet hours next need a separate design contract before runtime work.

[Optional data-health notices](DATA-HEALTH-ALERTS.md) now integrate the pure lifecycle with scheduled monitoring, default off when configuration is omitted. Optional `dataHealth` metadata shares `monitor:v1`; legacy records start a full activation grace without rearming battery latches. At most one independently validated `health` event shares the same two total slots, carries no fabricated `Reading`, and follows battery events in delivery order. Battery admission evicts/consumes health if it needs capacity. Corrupt optional metadata suppresses health with a fixed code while preserving battery cycles; malformed queue records still fail closed. Health-off legacy cooldown behavior is retained, and opting out clears only health metadata/events in one checkpoint even during cooldown. Whole-monitor disabled mode still does no KV/provider work.

The health send gate is independent: missing-data text can be delivered during a failed Deye request or cooldown, while stale battery advice and weather requests remain suppressed. It never bypasses Deye backoff, requests weather or adds a KV key. Recovery requires two fresh distinct source instants and recorded API acceptance of that episode's stale notice. Health windows/expiry/evidence are rechecked after waits; retries/exhaustion/eviction consume the original candidate, with no renewed TTL. First/result checkpoints and the at-most-two total Telegram attempts are shared. Status does not call or persist the lifecycle.

The offline `configureHealth` helper validates before prompting, clones settings, separately confirms opt-in/duration/delivery and requires a final save. No duration is preselected, nighttime consent is explicit, and daytime delivery reuses only the existing window. Opt-out removes only health settings; invalid saved consent yields a fixed recovery hint rather than silent repair. CLI saving uses the existing ignored local file and requires separate manual deployment. A shared pure configuration summary extends setup/preferences and authorized `/settings`/`/status`: it labels off/on/paused, independent battery switches and unverified operation/receipt. It never reads lifecycle metadata as readiness evidence, adds provider/KV operations, changes bot overrides or creates events. Invalid settings render fixed text in the pure summary; the webhook still validates all saved configuration and fails closed before replying. CI strictly allowlists only the four health fields, then applies shared consent validation. Defaults/template and personal configuration remain unchanged; CPU and live release gates remain.

The webhook requires its Cloudflare secret header plus the configured owner sender and destination chat. Payloads are capped at 8 KiB; old text commands/confirmation buttons are ignored or reported expired. Up to 48 ordinary sequential command writes/day are permitted, with a two-second spacing guard and best-effort update-ID filtering. State is saved before bounded one-attempt replies. KV eventual consistency still allows lost/duplicate replies or effects under concurrency/crashes. See [Telegram bot semantics](TELEGRAM-BOT.md) for settings precedence, bounds and failure behavior. Automatic EV detection is not implemented; a manual confirmation does not identify the cause of battery discharge.

Charging confirmations optionally render up to 12 configured-profile report buttons when EV hints are enabled. A callback is bound to the current active charging session's timestamp, a profile index and a SHA-256 context of its EV configuration (first 16 hex characters). It must arrive within 30 minutes, match current definitions and pass existing authorization/budget guards. The context is not an authentication credential. Changed/reordered definitions, stopped/replaced/expired/future sessions and disabled/absent profiles cannot alter a report. Selection updates only existing `session.profileId`; `at` and `expiresAt` remain unchanged. Legacy sessions need no migration; a new charging report offers the menu. A lazy invocation-local digest is reused for selection/rendering, with no new state/key, KV operation, provider request or growing cache. CPU for this work remains unmeasured in production. Replies distinguish manual reports from measured EV power and never grant an overnight exception.

Accept a reading only if it has numeric SOC in `[0,100]`, numeric non-negative `dischargePower`, a valid supported timestamp no later than the current clock, and age ≤ 600 seconds by default. The station adapter requires both measurements. Convert explicitly confirmed kW to W. Never coerce empty/null values or infer direction from `batteryPower`.

Equal timestamps are duplicates; earlier timestamps are out of order. Neither advances the state machine. Invalid or stale readings reset discharge confirmation. A gap > 720 seconds between accepted readings, or elapsed wall time since the last reading, also resets confirmation. This prevents one old high reading from combining with a much later one.

Full SOC ≥ threshold queues one full event and disarms it; SOC strictly below rearm threshold arms it. While discharge is armed, each accepted reading strictly above its threshold increments the counter, capped at two; a reading at/below threshold clears it. At two it queues an event, disarms, and clears the counter. Only discharge strictly below the rearm threshold arms it again. Intermediate values cannot cause repeated discharge alerts.

“Sustained” means observed at two distinct sample times, each fresh when evaluated; it is not proof of continuous discharge between samples or of an EV load. Five-minute polling cannot see short transients or detect their cause.

Optional `daytimeDischarge` replaces the discharge confirmation with an explicit installation timezone, same-day hour window (start inclusive, end exclusive) and 1–120 whole minutes of high samples. The runtime keeps a bounded `highStartedAt`, local `dischargeDay` and separate policy identity in the existing state record. Both source time and delivery time must be in the same open local window. Duplicate/out-of-order samples do not advance confirmation; low/invalid readings and long gaps reset its start. Each new local window rearms discharge; normal within-window rearm hysteresis remains strict. Existing all-day installations omit the option and keep their two-reading behavior.

Changing only this policy removes old discharge retries and starts a new discharge confirmation while preserving full-charge latches/events and measurement identity. The normal outbox remains capped at two events and keeps its attempts/expiry. Delivery is checked again after the first KV checkpoint to avoid sending after the window closes. Timezone formatting uses one replaceable cached `Intl.DateTimeFormat`; there is no unbounded cache, growing history, extra KV operation or external request. Cold/warm production CPU still needs measurement. The local `daytime:setup` command changes ignored preferences only; weather does not participate in this implementation.

The same formatter now supplies numeric Gregorian/Latin date parts, seconds and a long UTC offset for display. `displayTime` uses only the existing explicit daytime timezone, retaining legacy UTC formats when absent/UTC. Alerts retain readable month names; status/expiry retain numeric dates. Local labels include the configured name and offset at the source/expiry instant, disambiguating repeated daylight-saving hours. One formatter is retained and replaced on zone changes, shared by window checks and UI rather than a growing per-zone cache. No state/config schema or identity field is added. All comparisons, stored timestamps, durations, retry times and command-day boundaries remain absolute/UTC; weather and technical setup previews retain UTC. Expanded formatting adds unmeasured CPU.

Messages distinguish measured battery discharge from an unknown load breakdown. The current adapter cannot derive total home use or a household/EV power split. EV-enabled alerts show manual charging evidence before conditional advice; an active “not charging” report suppresses EV reduction/profile advice. Expired/future reports are unknown. Rendering uses the existing bot-state snapshot and send-time clock, with no extra reads/writes or upstream requests. EV-disabled alerts omit EV advice entirely. Manual evidence never changes battery transitions or identifies their cause.

## Notification preferences and charging profiles

`notifications` optionally contains boolean `full` and `discharge` switches. Omission keeps both enabled for compatibility. The state machine tracks cycles even while a category is off, but does not enqueue its events. Disabling a category removes its pending outbox entries; the monitor persists that cancellation even during an API cooldown, using one state write and no API calls. The normal path still uses at most two state checkpoints. Re-enabling does not retrospectively enqueue a latched cycle.

`ev.profiles` optionally contains 1–12 labelled discrete settings, each specified by current in amps **or** nominal power in watts, never both. IDs and labels are unique and bounded; values must respect the confirmed minimum and electrical configuration. Nominal power is a configuration estimate, not a measurement of actual EV demand. A MAX power rating is never converted into an asserted actual current. Profile-based messages list the supported options and require manual checking; they do not automatically select a setting or retain a generic intermediate amperage reduction that the car may not support. If profiles are absent, the original conditional reduction estimate remains available.

The `npm run preferences` wizard performs no network/secret access and writes only local ignored settings. Applying it to a deployed Worker still requires deployment. Interactive tests inject deterministic prompts and synthetic settings; no real installation data or live account access is used.

Its shared summary uses only existing configuration to label optional Telegram commands as locally enabled/off, without claiming pairing or deployment readiness. Manual upload, deployment, registration and owner receipt checks stay separate. Disabled/omitted commands leave pairing optional; weather context does not imply charging planning or overnight permission. Summary generation is pure and omits location/station identifiers. This laptop-only text adds no runtime code, state, provider request or KV/CPU cost.

The real setup adapter delegates to shared prompt flows, then performs its existing local secret/config writes only after a successful result. Synthetic rehearsal invokes those same flows with in-memory inputs and injected transports; it has no live-file or network fallback. Replacing Deye credentials retains the same bot/chat's owner binding while removing obsolete Deye login context. Changing bot token/chat clears owner/webhook fields and disables local commands until pairing. The adapter still requires explicit upload/deployment/registration; final writes are not a cross-file transaction. This setup-only work does not enter the Worker bundle or change KV/CPU/request budgets.

## Optional forecast context

`weather` configuration is optional and defaults off. Enabling requires finite latitude/longitude plus explicit eligibility for Open-Meteo's free non-commercial service. The laptop-only `weather:setup` wizard preserves other preferences and does not deploy. Weather settings do not enter the measurement identity or reset full/discharge cycles. Status/settings commands do not request weather; settings show enabled/disabled without coordinates. Authorized status decodes forecast context from its existing monitor-state read, renders its independent cache age and reuses the alert forecast validation/attribution. At one hour, values are hidden as stale; unavailable coverage, corrupt/future/wrong-location context and failed attempts cannot become current forecasts. Battery data and manual charging reports remain independent, including when no battery reading has been cached yet. Status does not change the attempt guard, write monitor state or add KV/provider operations. Disabled weather is omitted even if old cache data remains stored.

Only a due, telemetry-supported discharge notification in its permitted window can prepare a weather attempt. An hourly guard is saved in optional `monitor:v1.weather` by the existing first checkpoint before the public GET. The provider result shares the existing delivery-result checkpoint, requiring no new KV operations or keys. Cache state retains at most six consecutive UTC hourly points, retrieval/attempt/retry times and a location context. Invalid optional context is discarded independently of core state validation; it cannot break battery processing. A different configured location invalidates prior context, not battery latches. Disabled weather is dropped on the next running monitor invocation.

The fixed HTTPS endpoint is `api.open-meteo.com/v1/forecast`; requests use six forecast hours, `cloud_cover`, `shortwave_radiation`, UTC and Unix seconds. Exactly one HTTP attempt has a 1.5-second deadline, manual redirect rejection and a streaming 16 KiB limit. Units must be `%`, `W/m²` and `unixtime`. Accepted ranges are cloud cover 0–100 and radiation 0–2000 W/m²; an invalid result simply provides no context. Failures keep the hourly attempt guard, with longer Retry-After honored in the result checkpoint. Raw bodies, fetch exceptions and request URLs never leave this module. Weather errors do not enter Deye backoff or the battery retry queue.

Rendering uses three strictly future hourly times within the next three hours and a retrieval age under one hour. The text identifies rounded model forecasts, previous-hour radiation means, retrieval time and Open-Meteo/CC BY attribution. It makes no PV-power prediction, EV detection, recommended profile or nighttime exception. Weather unavailability never prevents the ordinary measured alert, except that the existing permitted-window check is repeated after the optional wait. Crashes/eventual consistency can lose cache updates or duplicate requests; there is no global rate/delivery guarantee. Optional work adds CPU and at most one HTTP subrequest per notification invocation; production CPU still requires measurement.

## Persistent delivery outbox

A battery event has a deterministic ID (`kind:readingTimestamp`), creation time, attempt count and retry time. A health event uses its notice kind, episode and original qualification time, plus private policy context for matching. The Worker checkpoints all transitions **before** contacting Telegram. A failed initial state write prevents sending. Both kinds share at most two pending records and one final result checkpoint; health has at most one slot and cannot displace a battery event.

On each run with a fresh accepted or duplicate reading:

1. Remove events older than 30 minutes or no longer supported by the current reading. Remove full events if SOC is below its trigger, and discharge events if power is at/below its trigger, even if hysteresis has not rearmed. An obsolete failed event does not re-trigger merely because it was removed.
2. Update pending message telemetry to this fresh reading, so a delayed amperage estimate reflects current observed discharge.
3. Attempt each due event once. Telegram `ok: true` removes it. Network failures, HTTP 408 timeouts, 429 and server errors schedule retry; most other failures abandon the event. There are at most three attempts, with backoff approximately 5 and 10 minutes plus up to 30 seconds of jitter, subject to five-minute Cron granularity. Honor longer `Retry-After`/Telegram `retry_after` values; expiry can occur before the next permitted attempt.
4. Checkpoint delivery results. This invocation spaces the two writes to the same KV key by at least 1.1 seconds, respecting the one-write-per-second limit. Timers do not count as CPU time.

An out-of-order, invalid or failed API reading suppresses pending **battery** delivery in that invocation. Dropping/exhausting a battery event keeps its cycle latched until the measurement crosses the rearm threshold. Health uses the independent lifecycle/window gate above and consumes expired/abandoned candidates rather than creating repeated reminders. This bounds message storms but can lose notifications after transport failures. Logs use fixed event codes; `telegram_sent` means API acceptance, not user receipt.

## Authentication and API backoff

`auth:v1` stores a bearer token, expiry and a SHA-256 fingerprint of its credential/region context. KV contains authentication secrets: restrict access to the Cloudflare account and namespace. Password hashes must be treated as secrets because they can authenticate. Raw passwords are never stored. Setup submits the hash following Deye's official sample; TLS stays enabled and redirects are rejected.

Deye's top-level `accessToken` may already include `Bearer`; normalization prevents duplicated prefixes. `expiresIn` is interpreted as seconds, with a 60-second early refresh and KV TTL. Cached tokens with a changed fingerprint are ignored. A cached-token HTTP 401 or unsuccessful Deye JSON envelope gets one reauthentication and one repeated logical request. The reviewed schema has no stable JSON auth-error table; the generic unsuccessful-envelope fallback is intentional and may refresh once for an unrelated application error. Freshly obtained tokens are never immediately refreshed again. HTTP 403/429/5xx do not trigger this fallback.

Each Deye HTTP operation has an eight-second timeout and at most two transient attempts. In-process backoff is 500 ms plus jitter, and only occurs if any required wait is ≤ 2 seconds. Longer rate-limit waits are persisted as `apiRetryAt` and suppress later API calls until permitted. Subsequent transient errors back off 5, 10, 20, 40 then 60 minutes. Permanent API/configuration failures use a one-hour cooldown. Invalid telemetry is checked again at the next five-minute poll. KV/config/secret failures outside that path are logged safely and retried by a later Cron invocation.

A bot token can appear in Telegram's required URL path; Deye's App ID is in the authentication query. Neither request URLs nor response bodies, telemetry, station identifiers or credentials are logged. The CLI prints selected telemetry only for explicit setup/preview and prints station names only during selection. Do not add raw exception logging or request tracing.

## Consistency and gaps in guarantees

Workers KV is eventually consistent. Reads in other locations may lag **60 seconds or more**, including cached missing keys; no strong same-location guarantee can be assumed. There is no atomic compare-and-swap or cross-invocation lock. Five-minute scheduling makes conflicts less likely but does not prevent them.

The two checkpoints are not transactional with Telegram. A crash after Telegram accepts the message but before the second checkpoint can cause a duplicate. A timeout may have accepted a message remotely. Concurrent runs can overwrite state or both send the same event. Corrupted/lost state, changing configuration and token-cache visibility can also change behavior. The tests intentionally demonstrate the crash duplicate.

This project promises neither exactly-once nor at-least-once delivery, and cannot guarantee zero lost notifications. If stronger coordination becomes necessary, evaluate a single Durable Object with transactional storage; it would still need an explicit policy for ambiguous Telegram sends. That is a separate design, not a claimed property of this KV implementation.

Deye, Telegram, Cloudflare, the logger and the network can all be unavailable. There is no separate channel for outage notifications in v1. Inspect account metrics and logs periodically. The system sends advice only; it does not issue inverter/charger commands, read EV current, or adjust equipment automatically.
