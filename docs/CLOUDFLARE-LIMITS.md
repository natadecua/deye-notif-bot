# Workers Free sizing and verified limits

Reviewed **2026-10-21** against Cloudflare's current official documentation. Limits can change; recheck before deployment and account for every other application in your account. Cloudflare's Free account quotas are not dedicated to this Worker.

| Resource | Documented Free limit | One five-minute monitor |
| --- | --- | --- |
| Worker invocations/requests | 100,000/day | 288 scheduled invocations/day; 8,640 per 30 days, 8,928 per 31 days |
| Cron Triggers | 5/account | 1 |
| Cron CPU | **10 ms/invocation** | Small JSON, state transitions and Web Crypto only; production CPU unmeasured |
| Memory | 128 MB | Two small KV values and small API responses |
| External subrequests | 50/invocation | Usually 1 Deye request; at most 6 Deye HTTP attempts + 2 Telegram attempts = 8; optional weather adds at most 1 |
| KV reads | 100,000/day | Up to 2/run = 576/day (state + auth cache) |
| KV writes | 1,000/day | Usually 1/run = 288/day; designed maximum 3/run = **864/day** |
| Writes to one KV key | 1/second | The two state checkpoints are explicitly spaced ≥ 1.1 seconds |
| KV storage | 1 GB/account | A few KB for state and token, no growing history |
| KV deletes / list operations | 1,000/day each | None in normal operation |

The read/write bounds assume a single configured Cron, one Worker, one station, no overlapping/manual invocations, valid KV responses and this implementation's bounded requests. A token is written at most once per invocation: either initially, or after refreshing a cached token. An unsuccessful fresh token is never renewed again in the same run. State is written once before delivery, plus one checkpoint after any attempted Telegram sends. Two pending alerts share that final checkpoint. This gives at most `(2 + 1) × 288 = 864` writes/day even with frequent token renewal. Typical daily use is close to 288 state writes, with rare notification checkpoints and token refreshes. Backoff/disabled runs can use less. Cancelling a disabled category's pending notification during API backoff uses at most one state write and no external API calls, within the existing bound. Custom profile settings are bounded to 12 entries and do not add KV reads/writes; production CPU remains unmeasured.

A renewal interval of roughly 60 days appears in Deye's token example; runtime always follows the actual returned `expiresIn`, not a fixed lifetime. Normal Deye polling is approximately 8,640 requests per 30-day month, plus setup/authentication/retries. Current Deye service-model notices discuss upcoming quotas/rate controls; do not assume a perpetual fixed free Deye allowance.

Worker invocation counts are conservatively budgeted against the Free request allowance. There is no dashboard, health-check traffic, public trigger endpoint, queue, paid database or centralized backend. Bundled Worker size from the local dry run is recorded in [validation notes](VALIDATION.md). Libraries used for interactive setup/testing/building are not bundled into the deployed Worker.

Optional [Telegram commands](TELEGRAM-BOT.md) add one bot-state read per Cron, plus up to 48 normal accepted command-state writes per UTC day. A status request reads the existing monitor cache and never calls Deye. Under the same stable-configuration/no-overlap assumptions, the combined write design bound is **864 + 48 = 912/day**, and reading use is approximately **576 + 288 + 96 = 960/day** if all 48 commands request status. A callback uses at most an acknowledgement plus one reply. The final command slot reports the daily limit; subsequent updates do not write/send. The two-second guard, a single webhook connection and KV markers reduce ordinary bursts, but cannot enforce a transactional global bound under concurrent/eventually-consistent reads. Extra account workloads still share quotas. The original table describes notification-only mode; webhook HTTP traffic and CPU also count and require live observation.

Optional daytime discharge filtering adds only bounded fields to the existing state and one cached timezone formatter. It does not add KV reads/writes, API calls, queue slots or history, so the above design bounds remain unchanged. Its timezone/date work adds CPU cost that has not been measured in production, including initial formatter creation.

Optional Open-Meteo context shares the existing `monitor:v1` first/result checkpoints: its hourly attempt guard is saved before the public request and up to six forecast points are saved with delivery results. There is no separate cache key, additional KV read/write, growing history or alert queue. The **864 / 912 write/day** bounds remain unchanged under the same assumptions. A stable installation can make at most about **24 weather requests/day**, only when a discharge alert needs context; full/muted/out-of-window/no-pending cycles do not call it. One optional GET adds at most one subrequest to a notification invocation (maximum **9** with core provider attempts). It has one 1.5-second attempt, a 16 KiB body cap, an hourly persisted guard and longer Retry-After handling. Configuration changes, missing/corrupted state or concurrent/stale KV reads can add requests beyond that normal bound. Production CPU, including validation/parsing/rendering, is unmeasured; the public reference-city weather smoke test does not establish deployed Free-plan behavior.

**The 10 ms CPU limit is material.** Network waits and timer waits do not count as CPU time, but parsing, hashing, validation and message formatting do. We use a dependency-free runtime and small response/state values. Local Node tests, workerd tests and deployment dry runs do **not** establish production CPU usage or Free-plan viability for every API payload. After live deployment, inspect CPU metrics/errors in your own account, especially cold/authentication runs. Any `Exceeded CPU Time Limits` failures can prevent persistence/delivery. Keep the Free plan; profile/reduce work before considering a different design. This project does not require or automatically enable a paid plan.

KV's one-write-per-second rule cannot be enforced globally by this Worker under concurrency. Do not run multiple Crons/Workers against one namespace or rapidly repeat manual polls. Other workloads can exhaust your account-wide allowance even if this monitor stays within its estimate.

Authorized `/status` renders optional weather from the same monitor cache read it already uses for battery data. It makes no Deye/weather request, writes no forecast guard or monitor state, and retains the single bounded Telegram reply plus normal command replay write. Existing read/write/subrequest design bounds are unchanged. Decoding up to six points and formatting up to three adds CPU that still needs live measurement.

Configured profile-report buttons use the existing bot-state read/replay write, one Telegram reply and, for callbacks, one acknowledgement. There is no monitor read/write, new state field/key, telemetry/weather request or extra retry. Up to 12 buttons use callback data of at most 44 ASCII bytes. At most one invocation-local SHA-256 digest of EV definitions is computed for eligible profile work; no global cache/history is retained. The 864/912 write/day and existing callback subrequest design bounds remain unchanged, under their existing assumptions. Production CPU for hashing/menu rendering still requires measurement.

Local battery reading/manual-expiry labels reuse the existing explicit daytime timezone and its single replaceable `Intl.DateTimeFormat`. It now includes minutes, seconds and an offset and is shared with window checks; no additional formatter map/history, KV/state/config field or provider request is added. UTC fallback uses the existing direct date formatting. The 864/912 write/day and subrequest design bounds remain unchanged. Additional `formatToParts`/offset rendering and the expanded formatter's cold/warm CPU still need production measurement.

Cached update/cooldown status reuses the existing authorized monitor read, bot replay write and single Telegram reply. It adds only fixed branches/text and, for a future representable retry threshold, the existing date formatter. It adds no provider request, KV operation/key, state field, queue event or polling schedule. The 864/912 write/day and status-read/subrequest bounds remain unchanged under the same assumptions. Rendering CPU remains unmeasured in production; no live availability or exact retry/delivery guarantee is implied.

## Proposed health notices: budget review (2026-10-24)

The official Workers limits/pricing, KV limits and consistency pages below were rechecked for the documentation-only [data-health proposal](DATA-HEALTH-ALERTS.md#refreshed-resource-envelope). Its calculation retains 288 polls/day, at most two monitor checkpoints plus one token write per run, and the existing **864/912 write/day** bounds by sharing the two event slots and two Telegram attempts. No new key, provider poll or checkpoint is budgeted. Typical cooldown-path writes could increase if health were implemented, even though the maximum is unchanged. CPU remains unmeasured; the proposal is not deployed or enabled. See its acceptance gates before changing runtime behavior.

The subsequent default-off runtime integration persists optional health metadata in the existing monitor record and shares the two event slots/Telegram attempts. Health-enabled cooldown ticks now use one monitor checkpoint, or two on delivery, with no Deye/auth/weather call; disabling health clears its metadata/events in one cleanup checkpoint. The legacy health-off path is retained. Unit assertions check the health-only one-read/two-write path and spacing, plus the failed-Deye three-write ceiling and queue capacity/priority; workerd intercepts the health-only Telegram request. No key, poll, history or third checkpoint is added, so calculated 864/912-write bounds keep their assumptions. Typical writes can increase when health is enabled. Owner setup, cached preference visibility, strict CI allowlisting and synthetic rehearsal have since passed local/runtime coverage; no installation was enabled or deployed. Current bundle measurements are in [validation notes](VALIDATION.md); decoding/lifecycle/text and larger cold-load CPU remain unmeasured against the 10 ms limit.

## Proposed daily recap: budget review (2026-10-27)

The official Workers/KV limits pages below were rechecked for the documentation-only [daily cached recap contract](DAILY-RECAP.md). It proposes no extra Cron, provider refresh, key/read, history or checkpoint: one recap would compete below battery/health for the existing two total slots/Telegram attempts. The same 288 ticks, at most two monitor checkpoints plus one token write, 864/912 daily write calculation and optional-command read estimate apply only under the existing assumptions. Its fixed original delivery opportunity expires rather than replaying missing days. Enabled recap ticks during Deye cooldown could increase typical writes while sharing that ceiling and making no auth/weather request; whole-monitor off remains zero IO. Additional bounded local-time/rendering/decoding CPU would require Free-account measurement. No recap behavior, state/config field, owner schedule or runtime cost is added by this design-only change.

The subsequent pure policy/slot-preparation foundation is deliberately outside the deployed Worker import graph. It adds no accepted deployment config/state field, queue kind, IO or bundle size; existing production CPU/request/KV paths are unchanged. Synthetic tests check fixed metadata size and constant formatter work, not production CPU. Future integration still must meet the proposed shared envelope and live-measurement gates above; no recap is enabled by publishing these helpers.

Shared snapshot rendering now serves existing authorized brief status, reusing its two reads, one replay write and one reply. Extracted detailed update text preserves its existing path. Fixed recap presentation, conditional command links and an explicit display-only zone add bounded branches/text and reuse the single formatter; no provider request, state/config field, queue slot, KV operation or scheduled recap call is added. The pure workerd harness makes zero outbound requests and does not establish Cron delivery. Updated bundle measurements are in [validation notes](VALIDATION.md); cold/warm production CPU remains unmeasured. The schedule-preparation module stays outside the deployed graph.

## Default-off recap integration (2026-10-28)

Subsequent monitor integration now imports preparation/rendering and persists optional recap metadata/events in the same record/checkpoints. No additional Cron, key/read, provider refresh, history, queue slot, Telegram attempt or result checkpoint is added. Priority is battery > health > recap, with skipped/evicted/expired dates consumed rather than replayed. Enabled cooldown ticks can use one state write, or two on delivery, without auth/Deye/weather calls; combined health/recap delivery can use both existing Telegram attempts. Typical cooldown writes can increase, while the existing two-monitor-plus-one-token ceiling retains the 864/912 daily calculation under its original assumptions. Recap-off legacy cooldown retains its zero-write path; opt-out cleanup needs one checkpoint, and whole-monitor off remains zero IO.

Synthetic assertions cover the one-read/two-spaced-write cooldown recap, two informational sends sharing one result checkpoint, normal/failed-provider three-write bounds and old-state/disabled compatibility. One workerd scheduled case intercepts only Telegram and preserves queued battery advice. The larger current bundle and enabled validation/formatting/queue CPU remain unmeasured in production; public defaults/private settings stay off and owner setup/CI enablement remain gated. See [validation notes](VALIDATION.md) for local results. The earlier design/foundation/rendering paragraphs describe their staged changes; preparation is now part of the deployed bundle, without any actual installation deployment or quota measurement claim.

## Proposed general quiet hours: budget review (2026-10-28)

The documentation-only [quiet-hours contract](QUIET-HOURS.md#resource-contract-and-source-review) rechecked the official Workers limits, KV limits and consistency pages. Free Cron CPU remains 10 ms; KV allows 1,000 daily writes and one write/second to a key, with eventually consistent cached reads. This is public documentation verification, not account/CPU testing. The proposal shares the existing 288 ticks, two monitor checkpoints, token write, two event/send slots and existing read/provider paths: the calculated 864/912-write envelope keeps its current assumptions. A less-than-128-byte monotonic-clock companion would use the same monitor record/checkpoints; typical enabled cooldown writes could increase, without auth/Deye/weather during cooldown. Selected quiet discharge skips weather preparation, and quiet hours never force a provider refresh or deferred replay. Future constant-work helpers and cold/warm Free CPU observations remain gates. No runtime dependency, field, cost, setting or behavior is added by this design-only change.
